# Автоматический учёт операций

Требуется CennikAddon **0.10.0**. Перезапустите веб Cennik после обновления,
обновите аддон через настройки, полностью перезапустите игру: в TOC добавлены
`Accounting.lua` и `AccountingCapture.lua`. Подтвердите рынок для каждого
персонажа. Учёт работает при загруженном аддоне, в том числе вне окна AH.

## Обычная работа

Играйте как обычно. Аддон наблюдает операции, веб принимает их через
SavedVariables после `/reload` или выхода из игры. При включённом автоимпорте
файл подхватывается автоматически; вручную — «Учёт» → «Загрузить из игры».
Следующий `/reload` загрузит подтверждение и освободит очередь передачи.
Вручную заполнять каждую покупку, крафт или продажу не требуется.

Автоматически поддержаны:

- Подтверждённые покупки рабочих заданий Cennik и снайпера, включая ручное
  подтверждение спорной покупки с соответствующей отметкой.
- Покупки через другие окна современного AH: наблюдение запроса, котировки
  и завершения. Покупка из аукционной почты служит дополнительным источником;
  получение уже учтённой покупки не создаёт второго расхода.
- Покупка и продажа у NPC: изменения сумок сверяются с фактическим изменением
  денег и ценами открытого продавца. Несовпадение даёт запись для сверки.
  Валютные/бартерные цены без однозначной стоимости золотом не выдумываются.
- Крафт через `DoTradeSkill` либо доступный современный рецепт: успешные
  заклинания и фактический расход/выход в сумках. Состав читается из API
  профессии. Ожидаемый выход рецепта не подменяет полученное количество.
- Распыление: заклинание, расход одного исходного предмета, окно добычи
  и фактически полученные материалы. Неполный или неоднозначный набор событий
  требует сверки, а не создаёт расчётные материалы в учёте.
- Выставление на AH, частичные продажи по полученной почте, возврат отменённого
  или истёкшего лота, известные залоги и их возврат. Пропажа лота из поиска
  не считается продажей. Для почты нужны достаточные сведения о выставлении,
  предмете, количестве и комиссии; неподтверждённые данные остаются для сверки.
- Почтовый перенос между известными собственными персонажами одного сервера
  и подтверждённый почтовый сбор. Каждый персонаж должен ранее зайти с этим
  аддоном. Получение переноса сохраняет стоимость и не считается покупкой.
  Неизвестный получатель не объявляется автоматически собственным персонажем.

Наблюдатель не выполняет покупки, крафт, распыление или получение почты за игрока.
Он не меняет завершённость рабочих заданий: «закупка завершена» остаётся
состоянием закупки, дальнейшая цепочка видна отдельно в учёте.

## Себестоимость и прибыль

Каждая покупка создаёт партию с фактическим количеством и общей стоимостью.
Сначала расходуются партии явно назначенного задания; при отсутствии назначения
используется FIFO по персонажу, серверу, предмету и варианту. Это правило учёта,
а не утверждение о физическом порядке расходования одинаковых единиц в стаке.
Себестоимость переносится из материалов в результат крафта и далее в проданную
часть. Остальная стоимость остаётся в запасах. При целочисленном делении
последняя единица сохраняет оставшуюся медь; стоимость не теряется на округлении.

Для нескольких материалов распыления общая стоимость входа распределяется
пропорционально количеству и справочной цене каждого выхода. Используются
явно уточнённые цены либо сохранённые при импорте цены рынка с датой не позже
операции. Они нужны для распределения одной стоимости, не для подтверждения
выручки. Последующие обновления рынка это распределение не меняют. Если цен
нет, стоимость распределения неизвестна; её можно уточнить в записи.

В вебе показаны отдельно:

- Прибыль по продажам с известной себестоимостью и известные расходы.
- Выручка после комиссии AH, без возвращённого залога.
- Покупки и денежный поток за выбранный период.
- Остатки по себестоимости за всё время, включая товар в пути и на AH.
- Продажи с неизвестной себестоимостью и операции для сверки.
- Партии стратегий: прогноз, закупки, продажи, прибыль, крафт и распыление.

Залог удерживается отдельно от прибыли. После подтверждения всех исходов лота
разница между уплаченным и возвращённым залогом становится известной потерей.
Деньги, возвращённые как залог, не являются выручкой. Комиссия из аукционного
письма не вычитается повторно из уже чистой выручки. При неполных данных о залоге
это обозначается в сводке.

Журнал использует **реальное время**, даже если аналитика работает с замороженной
датой разработки. Фильтр периода не обрезает историю расчёта себестоимости:
покупка до начала периода учитывается в более поздней продаже.

## Начальные запасы и исключения

Сумки персонажа при начале учёта фиксируются один раз как начальный запас
с неизвестной стоимостью. Старые запасы банка могут не попасть в этот снимок.
Неизвестная стоимость не считается нулевой и не создаёт выдуманной прибыли.
Если начальный запас пересекается с ранее записанным переносом, нужна сверка.

Уже существовавший журнал исполнения сохраняется. Его прежние покупки
автоматически не добавляются поверх нового начального остатка: это могло бы
дважды учесть товар. Новый учёт начинается с обновления аддона. Операции при
выключенном аддоне, нераспознаваемые варианты, неоднозначная почта, внешние
передачи и неподдерживаемые события клиента требуют уточнения. Рыночная оценка
товара не заменяет стоимость его приобретения.

В строке «Уточнить» можно изменить тип, состав, количество, сумму, привязку
к заданию и причину. Сумма продажи — **чистая выручка после комиссии, без
возвращённого залога**. У покупки и начального запаса сумма относится ко всей
указанной партии, а не к одной штуке. У выходов распыления справочная цена —
за штуку. Исходная запись сохраняется; исправление пересчитывает дальнейшую
историю. Ошибочную запись можно исключить с причиной и затем восстановить
уточнением. «Добавить пропущенную операцию» предназначено для исключений.

## Хранение и ограничения

Данные находятся в `data/cennik-next/accounting/events/`, по одному JSON на
операцию, с исходным событием и историей исправлений. Существующие SQL-схемы
не расширяются. Учёт включён в обычную резервную копию. Повторные импорты
идемпотентны, конфликт содержимого одного ID не перезаписывает историю.

Аддон передаёт до 500 операций за один цикл подтверждения. Остальная очередь
сохраняется до следующих `/reload` и синхронизаций. Лимит — 5000 неподтверждённых
операций: прежние записи не удаляются, переполнение и пропуски явно отмечаются.
Сбой импорта учёта сохраняет очередь и отображается отдельно от обычного обмена.
Данные разделены по рабочему профилю, серверу и персонажу; чужой профиль
не подтверждается автоматически.

Проверка настоящего клиента Forever после открытия сервера остаётся необходимой:
набор API и порядок событий могут отличаться. Проверки с имитацией событий
проверяют код и обмен, но не удостоверяют совместимость закрытого сервера.

## Проверки разработки

`tests/test_accounting.py` проверяет FIFO, частичные продажи, переносы,
распыление, неизвестную стоимость, округление, залоги, повторный импорт,
исправления, сохранение исходников и Lua-наблюдатели.
`tools/check_accounting_ui.py` проверяет полный круг на отдельном профиле,
включая автоматические события, SavedVariables, веб, исправление стоимости
и мобильный экран. Рабочие БД и игровые файлы для этих проверок не используются.

Источники для проверки структуры событий: [Blizzard UI / AuctionHouse API](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_APIDocumentationGenerated/AuctionHouseDocumentation.lua),
[Blizzard MailFrame](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_MailFrame/MailFrame.lua)
и локальные вызовы API установленного Auctionator. Сравнение подхода:
[TSM Ledger](https://support.tradeskillmaster.com/en_US/tsm-addon-documentation/tsm-addon-ledger).
