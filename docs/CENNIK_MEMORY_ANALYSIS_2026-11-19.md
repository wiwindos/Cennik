# Память и задержки Cennik: анализ 19 ноября 2026

Анализ выполнен без изменения настроек рабочего сервера и без удаления данных.
Измерения относятся к конкретным моментам: память заметно меняется между пересчётами.

## Подтверждено измерениями

| Показатель | Значение |
| --- | --- |
| RAM всей VM | около 3,8 ГиБ |
| Лимит RAM контейнера Cennik | 2 ГиБ |
| Предыдущие замеры контейнера во время задержек | почти 2 ГиБ |
| Контейнер в последующем замере | около 1,15 ГиБ |
| RSS основного процесса в последующем замере | около 949 МиБ |
| Максимальный RSS этого процесса | около 2067 МиБ |
| Swap основного процесса | около 110 МиБ |
| Файловый кэш контейнера | около 224 МиБ |
| Сохранённые JSON-срезы веба на диске | около 0,85 МиБ |
| Временные файлы DuckDB на диске | около 191 МиБ |
| Последние нормализованные сканы | 165 463, 298 643 и 312 211 строк |

Анонимная память процесса включает и Python, и нативные библиотеки DuckDB/Arrow.
Эти цифры нельзя трактовать как точный размер Python-объектов отдельно от DuckDB.
Лимит DuckDB в коде — 512 MB, два потока. Это лимит его менеджера памяти, а не всего процесса.

В cgroup зарегистрированы достижения лимита и ненулевая memory pressure; используется swap.
В исследованном cgroup события `oom` и `oom_kill` равны нулю. Убийство процесса OOM по этим данным
не подтверждено. Между замерами серверный процесс был перезапущен; анализатор перезапуск не выполнял.

## Раздувание скана в RAM

Локальный синтетический опыт на 50 000 строках, без пользовательской БД:

- упакованная строка: 1,19 МБ;
- живые объекты после `unpack_scan`: дополнительно 27,84 МБ Python;
- пик разбора: дополнительно 31,47 МБ Python;
- одновременная таблица Arrow: ещё 7,79 МБ нативных выделений.

Линейное приближение к 300 000 похожих строк даёт около 214 МБ для живых Python-строк и Arrow
или около 236 МБ при совмещении пика разбора с Arrow. Это оценка по синтетическим данным,
не измерение реального полного импорта. Она не включает JSON/Lua, сериализацию, БД и прочие задачи.

Текущий код сначала создаёт все словари предложений, затем целую Arrow-таблицу, одновременно
сохраняя исходные объекты. SQL-хелпер также выполняет `fetchall()` и строит полный список словарей.
Такие операции увеличивают пики при наложении импорта, просмотра рынка и аналитики.

## Повторные пересчёты блокируют обмен

`SourceUpdates.run('history')` выбирает до пяти предметов и для каждого вызывает `Workspace.refresh()`.
`refresh()` после изменившегося ответа синхронно вызывает `calculate()`. Таким образом одна задача
истории может выполнить до пяти полных пересчётов. Импорт полного скана также вызывает расчёт
до завершения обмена с Worker. Служебные задания и обмен используют один исполнитель.

Последние завершённые расчёты:

| Полный расчёт | Крафт → распыление |
| --- | --- |
| 129 с | 117 с |
| 364 с | 329 с |
| 306 с | 266 с |

Это подтверждает узкое место по времени, но само по себе не доказывает, что данная стратегия
удерживает основную часть RAM. Опубликованные результаты всех стратегий занимают около 13,3 МБ
в сериализованном виде; сложные Python-объекты и временные копии занимают больше.

## Что менять по приоритету

1. **Быстро подтверждать приём.** Сначала надёжно сохранять пакет/скан и выдавать подтверждение,
   затем планировать аналитику. Убрать синхронный полный пересчёт из `refresh()` каждого предмета
   и из пути подтверждения скана. Объединять изменения в один ожидающий расчёт.
2. **Не задерживать Worker обслуживанием источников.** Приём, подтверждения и просмотр состояния
   должны продолжаться во время загрузки истории и аналитики. Простое добавление потоков без
   бюджета памяти опасно: оно может увеличить одновременно живые наборы данных.
3. **Обрабатывать сканы порциями.** Разбор и запись ограниченными пакетами по строкам и байтам,
   без полной промежуточной Python-коллекции плюс полной Arrow-копии. Агрегаты книги считать в SQL
   или по ограниченным группам, сохранив точную арифметику цены за штуку и взвешенной медианы.
4. **Сократить копирование результатов.** Стратегии могут отдавать кандидатов постепенно;
   валидировать, ранжировать и сохранять их по мере готовности. Не держать одновременно весь
   исходный список и повторно построенный полный список моделей. Проверки контекста сохраняются.
5. **Ускорить крафт под распыление.** Профилировать поиск цепочек, повторные проверки выходов и
   общие подзадачи. Кэширование должно учитывать количество, цены и общий баланс излишков.
   Упрощение до независимой цены одного компонента изменит расчёт и не подходит.
6. **Изолировать тяжёлую аналитику при необходимости.** Отдельный процесс получает подготовленный
   неизменяемый срез, выполняет расчёт и завершается, освобождая память. Активная DuckDB сохраняет
   одного владельца: второй процесс нельзя просто открыть на запись или чтение поверх живого
   файла с другим процессом-писателем. Нужны подготовленный Parquet/Arrow-срез и проверка поколения
   при публикации. Бюджет памяти учитывать суммарно для API, расчёта, БД и кэша ОС.
7. **Добавить измерения пиков.** RSS и cgroup memory/swap/pressure по этапам импорта и расчёта,
   длительности, число строк, объём очереди. Для точного распределения Python-объектов нужен
   отдельный профиль выделений; текущих данных недостаточно для диагноза «утечка».

## Как проверять результат

- Полные сканы на 300 000 и 1 000 000 строк, повторяющиеся импорты и несколько отправителей.
- Одновременные обновления AHL/FYI, расчёт стратегий и открытие страниц веба.
- Во время расчёта подтверждения Worker продолжают поступать; приём не ждёт его завершения.
- Сравнение прибыли, партий, медиан, выходов распыления и цепочек с исходным алгоритмом.
- Наблюдение не одного прогона, а серии циклов: пики ограничены, память после циклов не растёт
  постоянно. RSS может не вернуться к исходной величине из-за аллокаторов; это отдельно от утечки.

Увеличение лимита RAM может дать временный запас, но требует оценки остальных сервисов хаба
на общей VM. Оно не устраняет повторные пересчёты и блокировку обмена.

## Результат последующего внедрения 19 ноября

Лёгкие расчёты отделены от расширенных; тяжёлые запускаются по кнопке в отдельном процессе.
Дополнительно найден широкий запрос рецептов: он разворачивал историческую принадлежность
всех версий в Python до отбора последнего снимка. В автоматическом наборе это проявилось
как 108–139 секунд на этапе простого крафта, поскольку именно он первым читал рецепты.
Отбор перенесён в SQL, компоненты ограничены выбранными версиями.

При проверке около 16:06 по Екатеринбургу текущая память контейнера была около 480 МиБ.
Это текущий замер после обработки, не обещание максимума под любой нагрузкой. Последний
лёгкий расчёт выполнился примерно за 16 секунд; в нём отсутствовали тяжёлые стратегии.
Веб API отвечал за 0,02–0,07 с внутри сервера. Worker получил manifest HTTP 200, два активных
обмена были подтверждены в локальных файлах состояния. В изолированном Linux-тесте дочерний
расчёт дал ожидаемую прибыль 277 меди и использовал около 89 МиБ RSS.
