# Cennik: новая рабочая база и объединение источников

Статус: исходный архитектурный проект и направления развития, 22 октября 2026.
Локальная версия уже реализуется отдельно от старых баз; фактические возможности
и ограничения описаны в [руководстве Cennik Local](CENNIK_LOCAL.md).
Числа в первоначальном макете демонстрационные. Разделы о будущей глобальной
оптимизации партий, резервировании и пересчёте только затронутых стратегий
не являются заявлением об их готовности.

## 1. Принятые требования

- Новая база начинается в отдельном каталоге `data/cennik-next/`.
- Существующие `ahledger.duckdb`, `data/analytics/ahledger.duckdb` и SQLite остаются
  на месте; автоматического переноса или подключения старой базы в новый профиль нет.
- Каждый собственный полученный скан хранится постоянно, включая строки,
  которые не прошли нормализацию. История не заменяется суточными агрегатами.
- Сжатие и дополнительные агрегаты разрешены, удаление исходных сканов — нет.
- AHledger используется экономно: таблица цен, необходимые справочники,
  дополнительные данные по запросу. Полный исторический обход выключен.
- Веб служит для поиска и планирования; аддон — для актуальной проверки и
  исполнения подтверждённых игроком действий.
- Неизвестные цены и количества остаются неизвестными. Неполный расчёт не
  публикуется как полная прибыль, спрос не называется гарантированной продажей.
- Работа локальная, без Docker и дополнительного сервера СУБД.

## 2. Что сохраняем из существующего проекта

В проекте уже есть границы `MarketDataProvider`, `Strategy`, отдельные движки,
реестр стратегий, денежные расчёты, SQLite результатов, FastAPI и Bridge.
Полная перепись не нужна.

Сохраняем модели и формулы, где их семантика остаётся прежней: комиссия, ROI,
минимальный гарантированный выход, версии рецептов, ограничения CraftGraph,
правила отсутствующих данных, протокол пакетов аддона и ручное подтверждение
покупок. Меняем поставщика данных и добавляем расчёт закупки по доступному объёму.
Стратегии придётся адаптировать к этим возможностям; один новый провайдер сам по
себе не превратит текущую оценку одной единицы в точный план партии.

Новые пространства имён и экран работают рядом со старой панелью. Переключение
профиля явное. Старый загрузчик остаётся отдельным инструментом архива, но не
запускается из обычного обновления нового рабочего пространства.

## 3. Хранилища и выбор СУБД

Предлагается одно логическое рабочее пространство с тремя составляющими:

| Составляющая | Содержание | Зачем |
| --- | --- | --- |
| `state.sqlite` | Настройки, задания, HTTP-кэш, результаты, планы, исполнения | Короткие транзакции и быстрые ответы интерфейсу |
| `market.duckdb` | Справочники, последние наблюдения, рабочая книга предложений, сводки | Пакетные соединения, группировки, аналитические запросы |
| `archive/` | Неизменяемые собственные сканы и производные Parquet-разделы | Постоянное хранение без раздувания ежедневных запросов |

DuckDB выбран для аналитической части, а не для всех данных приложения. Он
встраивается в Python, умеет читать выбранные столбцы/разделы Parquet и подходит
для расчётов по многочисленным наблюдениям. Это не обещание фиксированной скорости:
объём, запросы и ограничения памяти всё равно нужно измерять.

SQLite остаётся для частых точечных операций. В WAL чтения и запись могут идти
одновременно, но писатель один. PostgreSQL разумен при нескольких независимых
пишущих сервисах, удалённых пользователях и требованиях серверного размещения;
для одного локального процесса сейчас добавит эксплуатацию без доказанной пользы.
Менять текущую закреплённую версию DuckDB ради этого проекта не требуется.

Конкурентность: один процесс Cennik владеет пишущими подключениями DuckDB;
импорт проходит через одну очередь. Чтения и расчёты — отдельные подключения
того же процесса с совместимой конфигурацией и фиксированным снимком транзакции.
Bridge и отдельные CLI не пишут в DuckDB напрямую: передают задания локальному API.
Первый запуск — один worker Uvicorn. Несколько пишущих процессов не поддерживаем
путём повторов ошибок блокировки; это потребовало бы другой архитектуры.

## 4. Каталоги новой базы

```text
data/cennik-next/
  workspace.json                  # UUID профиля, версия схемы; старые пути не подставляются
  state.sqlite                    # оперативные данные нового профиля
  market.duckdb                   # рабочая аналитическая база
  archive/
    scans/<market>/<year>/<month>/<day>/<scan_id>.json.zst
    normalized/<schema>/<market>/<year>/<month>/<day>/<batch_id>.parquet
    api/<dataset>/<year>/<month>/<request_id>.json.zst
    manifests/                    # версии схем, перечни файлов, контрольные суммы
  cache/                          # восстанавливаемые ответы дополнительных API
  staging/                        # незавершённые приёмы, не источник для расчёта
  logs/                           # ограниченная ротация журнала
  backups/                        # место для локальных контрольных копий
```

`archive/scans` не имеет TTL или автоматической очистки. Объединение Parquet —
только создание производных представлений; исходный скан и его строки остаются.
Одинаковое содержимое допускает общее физическое хранение, но сканы разных
моментов остаются отдельными событиями. Повторный импорт того же события не
создаёт нового наблюдения. Одинаковые строки внутри одного скана не удаляются:
два одинаковых стека могут быть двумя объявлениями.

Последние наблюдения и рабочая книга в DuckDB — заменяемые проекции. Обновление
этой книги не означает удаления исторического скана из архива.

При нынешней пробе из 15 644 строк и 96 сканах в сутки получится около 1,5 млн
строк в сутки и 548 млн в год. Это сценарий непрерывного сбора каждые 15 минут,
а не прогноз фактической доступности. Упакованная строка текущего примера занимает
259 199 символов: порядка 9,1 ГБ/год до сжатия, метаданных и производных таблиц.
После роста рынка число может быть существенно больше. Размер Parquet и степень
сжатия заранее не обещаем: измеряем на неделе реального сбора.

Постоянное хранение требует места и резервной копии вне этого диска. При нехватке
места запись останавливается с видимой ошибкой; архив не освобождается удалением
старых сканов. Копирование открытых файлов БД не считается резервным копированием:
нужны согласованный checkpoint/закрытие DuckDB, SQLite backup API и манифест архива.

## 5. Основные сущности

### Справочники и наблюдения — DuckDB

| Таблица | Ключевые данные |
| --- | --- |
| `markets` | Точный realm/ruleset/faction/region/game, сопоставление с AHledger |
| `items`, `item_variants` | ID, локализованные имена, ссылка/ключ варианта, свойства |
| `recipe_versions`, `recipe_inputs`, `recipe_evidence` | Неизменяемая механика, происхождение, принадлежность актуальному пакету |
| `scan_registry` | scan_id, источник, рынок, build, начало/конец, импорт, count, completeness, hash, путь |
| `quote_observations` | Минимум, медиана, количество как единое наблюдение одного источника |
| `source_estimates` | Медианы 7/30 дней, оценка продаж, методика, отдельная свежесть |
| `working_offers` | Строки последнего применимого полного скана, item/variant, count, цена стека |
| `current_market_view` | Выбранные наблюдения и ссылки на отдельно датированные книгу и оценки |
| `hourly_summary`, `daily_summary` | Производные сводки, источник и метод расчёта |
| `recipe_dependencies` | Обратные связи предмет → зависимые рецепты, включая цепочки |
| `applied_ingestions`, `dataset_revisions` | Завершённые импорты и версии для воспроизводимого расчёта |

Все исходные строки доступны через архив и Parquet, но не обязаны постоянно
лежать в одной таблице `working_offers`. Строка replicate не получает выдуманный
AuctionID: позиция внутри скана — технический идентификатор наблюдения.

### Оперативные данные — SQLite

`workspaces`, `settings`, `source_health`, `ingestion_jobs`, `http_cache`,
`enrichment_requests`, `analysis_runs`, `opportunities`, `plans`, `plan_inputs`,
`addon_packages`, `execution_events`, `transactions`, `publication_outbox`.

Каждый результат хранит набор использованных revision/scan/source/recipe IDs,
конфигурацию, версии стратегий и `as_of`. Локальное время интерфейса —
Asia/Yekaterinburg; все времена хранения — UTC. Денежные итоги — целая медь,
сравнения дробной цены единицы — точные отношения/Decimal, не float.

## 6. Приём собственного скана

1. CennikAddon запускает штатный массовый скан Auctionator и читает общий ответ.
   Аддон AHledger не требуется и не используется как файловый источник.
2. Bridge читает `CennikAddonDB.market_scans` из сохранения CennikAddon. Lua
   разбирается как данные, без исполнения кода. Проверяются стабильность файла,
   размер, рынок, время, формат, число строк и денежные диапазоны.
3. Записываем извлечённый скан в неизменяемый архив через временный файл,
   fsync и атомарное переименование; считаем SHA-256 именно нового объекта.
4. Нормализуем ограниченными пакетами. Невалидные строки остаются в исходнике,
   получают причину в отчёте. Такой пакет не объявляется безусловно полным.
5. В транзакции DuckDB добавляем registry, сводки, проекции и запись applied_id.
   Пригодный полный снимок целиком заменяет предыдущую книгу этого источника.
6. После commit фиксируем успешное задание в SQLite и событие изменения данных.
   Затем запускается выбранная пользователем политика пересчёта.

Общей транзакции между файлом, SQLite и DuckDB нет. Поэтому применяем идемпотентный
протокол: неизменяемый объект → DuckDB с applied_id → подтверждение задания.
После сбоя сверяем журнал с applied_id; повторяем только незавершённое, не
публикуем незафиксированное. Лишний завершённый файл сохраняется для восстановления.

В новом профиле предел обменного Lua-парсера увеличен до 64 МБ. Очередь коллектора
ограничена тремя сканами и суммарным размером, без удаления неподтверждённых данных.
Превышение поддерживаемого формата
должно давать видимую ошибку, сохраняя доступный исходный объект для восстановления.

Проверка count подтверждает прочитанность полученного ответа, но не доказывает
полноту серверного рынка. Храним отдельно заявление источника `full`, собственную
валидность и фактическое покрытие. Неполный скан не обнуляет отсутствующие предметы.

### Условия непрерывного сбора

Режим коллектора Cennik повторяет запрос при открытом аукционе после разрешённого
интервала и готовности Auctionator. Очередь — максимум три снимка, без потери
неподтверждённых данных. SavedVariables видны внешнему процессу после reload/выхода.
После импорта второй reload загружает ACK и освобождает очередь. Полностью
непрерывная передача на диск без reload/выхода не реализована.
Нужно отдельно проверить сохранение и восстановление на Forever. Работа
24/7 — цель режима, не гарантия при отключениях клиента, сервера или диска.
Скрытое управление вводом и автоматические покупки в проект не входят.

### Варианты экипировки

Собственный коллектор Cennik сохраняет ID, количество, выкуп, ставку, категорию
времени, доступные ссылки вариантов, признаки делимости и известное владение.
Сохранение AHledger не используется. Без варианта и известной делимости стека
точный исполнимый план не формируется. Commodity-покупки всё равно требуют
адресной котировки игрового API.

## 7. Минимальное получение AHledger

| Набор | Политика |
| --- | --- |
| `markets` | При настройке профиля и ручном обновлении справочника |
| `pricetable` | Один ответ на рынок, общий кэш между заданиями, ETag/TTL |
| Карточки предметов | Для новых ID и по необходимости, с кэшем |
| Рецепты | Отдельная задача по профессиям при старте и изменении build/по расписанию пользователя |
| История предмета | По запросу карточки/исследования; сначала имеющийся архив, затем API |
| `structure`, `signals`, `deals`, `disenchant` | При открытии соответствующей функции/включении стратегии; единый ответ на рынок с явным top-N |
| Глобальная экономика, health, документация | Только соответствующий экран/диагностика, вне обычного обновления цен |

Проверка `pricetable` не является проверкой всех наборов: рецепты и оценки
могут измениться независимо. ETag — версия ответа, а время скана — свежесть
наблюдения. Новый ETag без нового времени не объявляется новым сканом.
304 ничего не добавляет в историю наблюдений; успешная проверка фиксируется отдельно.

Обогащение — явное асинхронное задание с дедупликацией одинаковых ключей,
ограничением параллелизма, Retry-After, тайм-аутом, кэшем и отменой неначатых задач.
Открытие карточки может заказать только показанный пользователю недостающий
набор; наведение/прокрутка не запускает бесконтрольную очередь.

Расчёт работает по уже зафиксированному набору данных и не ждёт HTTP внутри
обхода CraftGraph. Новый ответ создаёт отдельную revision и новый расчёт.
История API по умолчанию кэшируется ограниченно (например, 30 дней); правило
не применяется к собственным сканам. Использованный в сохранённом результате
ответ и его происхождение закрепляются в архиве, чтобы результат можно было повторить.
Кэшированные неиспользованные ответы можно удалять по TTL.

## 8. Выбор источника

Единого поля «самая точная цена» недостаточно. Разделяем:

- текущую сводную котировку;
- распределение доступного объёма с собственным временем и покрытием;
- исторический ориентир и оценку спроса со своими временем и методикой;
- подтверждённую адресную котировку для исполнения.

Сначала проверяем рынок, build/версию, вариант, область покрытия, допустимость
времени и полноту. Затем выбираем самое свежее подходящее наблюдение; при равной
свежести — более детальное. Сильное расхождение не усредняем: показываем конфликт
и требуем адресной проверки. Возможный сдвиг часов клиента отмечаем отдельно.

Пример: сводка AHledger 12:05 новее своей книги 12:00. Минимум 12:05 можно
использовать для ориентировочного поиска, но нельзя присвоить его старым стекам.
План по книге 12:00 остаётся датированным 12:00 и требует проверки. Новый полный
скан своего источника заменяет его прежнюю книгу; отсутствующие позиции не
подмешиваются из старой книги. Неизвестное покрытие не означает нулевое предложение.

Количество разных источников не суммируется. Скан, который мы отправили AHledger
и получили обратно агрегированным, не считается вторым независимым свидетельством.
История разных методик не смешивается в одну медиану без определения алгоритма.

## 9. Экономика и предел точности

### Два режима оценки

`предварительно` — известны только сводные минимумы. Быстрый поиск кандидатов;
никакого умножения «минимальная цена × всё количество» как точной закупки.

`по снимку` — хватает полной книги с известными вариантами и правилами стеков.
Закупка считается для указанного объёма по уровням цен. Это предложение на
момент снимка, а не резервирование. Неполная книга даёт только подтверждённую
часть затрат/диапазон, а полный итог остаётся неизвестным.

Адресная проверка добавляет отдельный статус входных цен «проверены в игре».
Он не превращает прогноз продажи результата крафта в исполненную продажу.
В интерфейсе это разные поля, а не один зелёный флажок «всё проверено».

### Закупка и CraftGraph

- Цена стека хранится целиком. Для неделимого лота покупается целый стек;
  избыток увеличивает необходимый капитал и не превращается в выдуманную выручку.
- Для делимых товаров считаем стоимость запрошенного количества по ценовым
  уровням, затем подтверждаем котировкой API покупки.
- Несколько задач делят виртуальный бюджет и резерв количества: одна доступная
  единица не обещается одновременно нескольким планам.
- NPC-цена имеет источник, время и условия доступа/скидки. Известную цену из
  справочника можно использовать с соответствующей отметкой. Неизвестная цена
  требует ввода/наблюдения; отсутствующие затраты не приравниваются к нулю.
- Рецепты выбираются по актуальной подтверждённой версии; доступность профессии,
  рецепта и отката конкретному персонажу — отдельные условия.
- CraftGraph сохраняет ограниченный поиск, гарантированный минимальный выход,
  контроль циклов и отсутствие прибыли от случайных бонусов/лишнего выхода.
- Убывающая доступность меняет стоимость партии: линейный cache «цена компонента»
  больше не годится. Планировщик получает общий набор предложений и потребностей.
  Ограниченный поиск не называется глобальным оптимумом; лимит показывается.

Доход NPC при подтверждённых условиях детерминирован. Доход от продажи игроку —
сценарий: текущий минимум предложения, осторожный исторический ориентир или
заданный пользователем предел. Сценарии показываются отдельно. Учитываем известную
комиссию, депозит и расходы; неизвестные будущие перевыставления показываем как
исключённые/сценарные, а не гарантированно нулевые. ROI считается от полного капитала.

AHledger estimated sales — оценка, а не вероятность продажи за час. Расходование
предложения между сканами не считается сделкой. Реальные собственные продажи
накапливаются отдельно; оценку времени продажи вводим только при достаточной
истории с видимым покрытием, включая непроданные и снятые объявления.

## 10. Быстрый и воспроизводимый пересчёт

Версия данных — не SHA-256 всей DuckDB. При импорте нового объекта считаем его
хэш один раз; транзакция меняет нужные `dataset_revisions`. Расчёт фиксирует вектор
версий цен/книги/рецептов/оценок и `as_of` на старте. Получение новых данных не
меняет уже открытый расчёт задним числом.

Изменившиеся ID → обратный граф зависимостей → затронутые стратегии и планы.
Смена версии рецепта и ограничений может затронуть большие участки; полный
пересчёт доступен явно. Первая инициализация всегда полная. Если изменился почти
весь рынок, работы также будет много — ускорение не обещается одним названием
«инкрементальный режим».

Обновления очереди объединяются, но ни один собственный скан не теряется в
архиве. Пересчёт рабочей выдачи может пропускать промежуточные revisions и брать
последнюю. Истечение свежести инвалидирует планы даже без изменения цен; кэш
имеет `valid_until`. Настройки, комиссия, стратегия, доступ персонажа и методика
исторического ориентира участвуют в ключе результата.

По умолчанию сначала ручной пересчёт. Отдельная явная настройка включает
автопересчёт после новых данных с ограничением частоты. Открытие страницы не
включает ни сеть, ни вечный цикл. Фоновый сбор включается настройкой источника,
виден в интерфейсе и останавливается отдельной кнопкой.

Публикация в SQLite атомарна: завершённый набор возможностей и указатель на него.
Обновившаяся во время расчёта версия не выдаётся за текущую; показываем возраст
результата и ставим следующий пересчёт, если автоматический режим включён.

Это карта целевых обязанностей, а не требование заранее создавать пустые модули.
Загрузчик и HTTP-ограничения переиспользуются. Новая UI может оставаться модульным
HTML/CSS/JS: React, отдельная сборка, Redis и микросервисы не являются условием.

## 12. Веб: шесть разделов

Общая верхняя строка: рабочее пространство, активный рынок, возраст своего
снимка и AHledger, состояние Bridge. Время отображается явно. Выбор AHledger
вебом не доказывает фактический рынок персонажа — соответствие подтверждается
данными игры. Технические пути, SQL и большие JSON находятся в диагностике.

| Раздел | Содержание и основные действия |
| --- | --- |
| Возможности | Стратегия, товар, объём, капитал, прибыль по сценарию, ROI, спрос, свежесть; открыть расчёт, добавить в план |
| Рынок | Поиск ID/названия, варианты, сводная котировка, книга уровней/стеков, отдельные источники; запросить историю |
| Архив сканов | Каждый скан, время, count, покрытие, ошибки, размер, экспорт; сравнить два снимка, включая неизменившиеся |
| Исполнение | Планы, материалы, общий бюджет, проверка в игре, покупки/продажи; фактический результат отдельно от состояний сканирования |
| Источники | Свой сборщик, AHledger, справочники: включение, очередь, TTL, последний успех, ошибка, повтор, запись на диск |
| Настройки | Стратегии, пороги, персонаж, риск/бюджет, свежесть, расписание, архив, резервные копии |

Главный экран не начинается с формы полного скачивания. Сразу видны возможности
и причины недоступности расчёта. Фильтры компактные, подробные настройки — в своём
разделе. Длинная диагностика открывается по запросу, с пагинацией и экспортом.

Карточка возможности раскрывает пять частей: экономика; закупка по объёму;
этапы крафта; источники/свежесть/конфликты; сценарии продажи и недостающие данные.
Изменение объёма пересчитывает капитал, затраты и прибыль по книге, а не просто
умножает значение одной единицы. Загрузка истории видна отдельным состоянием;
не блокирует просмотр уже имеющегося расчёта.

Статусы не смешивают техническую полноту и торговую пригодность:
`нет данных`, `предварительная оценка`, `закупка по снимку`, `нужна проверка`,
`входные цены проверены в игре`, `исполнено`, `ошибка`. Отрицательная прибыль
показывается явно. Передача в аддон доступна только после проверки обязательных
полей пакета, причин блокировки видно рядом с кнопкой.

Три разных действия: «Обновить данные AHledger», «Импортировать записанные сканы»,
«Пересчитать». Веб не обещает запустить игровой запрос из HTTP-кнопки. Настоящий
скан требует доступного аддона и открытого аукциона; команда мосту, если появится,
должна иметь подтверждение получения, а не оптимистическое «готово».

В макете можно переключать разделы, выбирать возможность, менять объём, сравнивать
свежесть источников и моделировать адресную проверку. Сеть и покупки не выполняются.

## 13. Предлагаемый контракт API

- `GET /api/v2/workspace`, `GET /api/v2/overview` — профиль и компактный статус.
- `POST /api/v2/sources/{id}/refresh` — явное задание, возвращает job_id.
- `GET /api/v2/jobs/{id}` — этап, счётчики, ограниченная ошибка; не полный сырой JSON.
- `GET /api/v2/scans`, `/scans/{id}`, `/scans/{id}/rows` — пагинация и фильтры.
- `GET /api/v2/items/{id}` — вариант, сводка и отдельно датированная книга.
- `POST /api/v2/enrichment` — разрешённый тип данных + market/item/range; без произвольного URL.
- `POST /api/v2/analysis` — запросить полный/затронутый пересчёт.
- `GET /api/v2/opportunities`, `/opportunities/{id}` — текущая публикация.
- `POST /api/v2/plans` — объём, бюджет, выбранные наблюдения; расчёт новой партии.
- `POST /api/v2/plans/{id}/publish` — существующий обмен с аддоном.
- `GET /api/v2/executions` — торговые события отдельно от технических сканов.

Синхронизация локально сохраняет текущую модель доступа к loopback; при удалённом
размещении используются существующая авторизация и ограничения. События статуса
можно отдавать через SSE с восстановлением по id и ограниченным polling fallback.
Сами изменения состояния выполняются обычными валидированными HTTP-запросами.

## 14. Этапы реализации и критерии готовности

1. Новый профиль и схемы, без подключения старых БД. Импорт одного уже имеющегося
   скана, читаемый отчёт и архив. Повторный импорт идемпотентен, старые файлы не меняются.
2. AHledger минимум + общий кэш + resolver. Проверить случаи нового времени,
   304, нового ETag без нового скана, отсутствия данных, конфликта вариантов.
3. Новый веб, предварительные стратегии и расчёт партии по глубине. Проверить
   неделимые стеки, недостаток количества, NPC, общие материалы, лимиты графа.
4. Адресная проверка/исполнение, обратная связь и реальные сделки. Возраст данных,
   итог неизвестен при пропущенных расходах, действия покупки подтверждает игрок.
5. Явный непрерывный сбор и инкрементальный пересчёт. Проверить запись/ACK,
   отключение игры, перезапуск процесса, повреждённый/частичный файл и полный диск.
6. Длительный прогон и резервное восстановление. Сравнить результаты полного
   и затронутого пересчёта на одинаковых версиях, замерить память/время/рост архива.

Проверки контрактов импорта, ACK, денежных расчётов, резервного копирования,
установки аддона и веба включены в локальную реализацию. Длительный прогон
в игре и сравнение будущего частичного пересчёта остаются отдельными этапами.

## Источники решений

- [DuckDB: конкурентный доступ](https://duckdb.org/docs/stable/connect/concurrency):
  обосновывает один процесс-владелец встроенной базы; серверные расширения не нужны.
- [DuckDB: работа с Parquet](https://duckdb.org/docs/stable/data/parquet/overview):
  выбор столбцов и фильтров позволяет читать нужную часть архивных данных.
- [SQLite WAL](https://sqlite.org/wal.html): оперативные чтения и короткие записи,
  ограничения единственного писателя и требования к резервному копированию.
- [AHledger API](https://ahledger.com/developers): ETag, кэш, времена данных,
  агрегаты и ограниченные рыночные выборки.
- [AHledger: сохранение скана](https://ahledger.com/get-started): reload/выход перед
  чтением внешним sync. Ограничения очереди и полей дополнительно проверены в
  установленной версии AHledger 0.9.6; собственный код при проектировании не менялся.
